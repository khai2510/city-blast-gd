# FX28 — win fireworks: brighter, more colours, twice the shots (Khai 28/11, D-blast-FIREWORK2)

Khai: "màu của cái pháo hoa nó phải sặc sỡ hơn nữa, đa dạng màu sắc hơn nữa. Số lượng nó phải bắn nhiều gấp đôi cho tới bây giờ."
Nothing else changes: no new feature, no reward change, no text, no sound.

Code: `src/main/ui2.js`, section **W** (`FX28`, `FWC`, `FW28`, `fxWin28()`, the pool, CSS `.cf.u2.gl` / `.x28`).
**`?fx28=0` = exactly the FW-1123 show** (old palette, 6 bursts, 154 pieces, `fxWin0()` is the old code unchanged).

## Where the win fireworks fire (all covered)
One function, `fxWin()` (ui2), for every level type: it runs when the meter passes with CLEARED! (`bumpPill` while
boom / settle) or at the latest on the win result (`showResult`, `ok && !manual`). Normal, Hard and Boss levels and the
g7 hard levels from Mac all go through these two calls (the g7 engine in `pipeline7/engine.js` wraps neither; nothing in
Mac's files had to change, no SYNC request). The other two win piece sets: the 42 Q7 stamp pieces (`v13-feel`) take the
firework palette through CSS `nth-child`, so they get the new 10 hues too; the base `confetti()` (40 pieces in `#confetti`,
z-index 2, behind the HUD) keeps its count.

## Before → after (count = pieces; measured, `__blast.ui2.fx()`)
| | before (`?fx28=0`) | after |
|---|---|---|
| bursts (shots) | 6 | **12** (×2) |
| rockets / pop flashes | 4 / 6 | 8 / 12 |
| pieces per burst | 24 | 24 (20 coloured + 4 white glitter) |
| **total firework pieces** | **154** | **308** (×2) |
| peak pieces on screen at once (opacity > 0.05) | 74 (at 0.7 s) | 148 (at 0.95 s) |
| hues | 9 soft-bright (incl. white), 3 per burst | **10 fully saturated** + white glitter, **4 per burst** |
| show length (last piece gone) | ~2.4 s | ~2.8 s |

Palette: hot pink `#FF1A8C` · red `#FF2424` · orange `#FF7A00` · gold `#FFC800` · lime `#A8FF00` · green `#00E85C` ·
cyan `#00E1FF` · electric blue `#2F5BFF` · violet `#9B30FF` · magenta `#FF2EF0` (+ white glitter). Each burst takes 4 hues
spread round the wheel (start +0 / +2 / +5 / +7, the next burst 3 further on, random start per win), so no two bursts in a
row look alike. Each burst is a two-tone peony: hues 1–2 fly out fast (outer ring), hues 3–4 slower (inner ring); the pop
flash is tinted with the burst's colour; rockets take the burst's first colour; 4 white glitter sparks per burst twinkle
(opacity keyframes) as they fall. Colour-changing trails were left out: animating `background` is not compositor-only and
would repaint every piece every frame.

Timing: 12 bursts 150 ms apart (was 6 at 280 ms), same 3 launch points (bottom-left, bottom-right, top-centre), pop points
spread wider (corner pops alternate inner / outer and high / low; the top shell walks left / right / centre) so the doubled
bursts do not stack on each other.

## Phone cost (no frame-time added)
- **Pool**: 330 `<i>` pieces made once (on level start, `display:none` while idle: no layer, no style cost); a win creates
  no DOM nodes, a finished piece goes back to the pool (its animation cancelled).
- **Per-burst start**: each burst's ~26 animations start at its own turn (a timer per burst; WAAPI delays inside), so the JS
  of a win is 12 small slices instead of one big frame.
- Same as before: WAAPI transform + opacity only (compositor), the `#feelLay` layer, reduce motion = none.

Measured (`fxprobe.js`, real L1 win with the level's own solution, 393×852, `?fps=1` probe; headless SwiftShader VM under load):
| | before | after |
|---|---|---|
| JS of the win frame (`fxWin()` call) | 4.5 ms (all 154 at once) | **2.0 ms** (first burst), worst burst slice 1.6 ms |
| same with all 308 at once (first try, no per-burst start) | — | 9.1 ms → why the per-burst start was added |
| frame interval over the 3 s show, real win (median / p90 ms) | 72.7 / 80.9 | 87.3 / 98.3 |
| JS per frame over the show (mean ms) | 5.90 | 6.43 |
| canvas hidden (DOM / compositor cost alone), rAF median / p90 / max ms | 16.7 / 16.7 / 16.8 | 16.7 / 16.7 / 16.8 |

Read: the headless frame interval is ~95 % SwiftShader GPU fill of the 3D canvas (LEARNINGS PERF-1124) and swings with the
VM load (the two runs were 20 min apart, load ~4.3 on 4 cores); with the canvas hidden the doubled show holds 60 fps exactly
like the old one (181 frames in 3 s, worst 16.8 ms), and the biggest JS slice of a win fell from 4.5 to 2.0 ms.

Hard level (slot 7 "Grand Arch", real win): 308 pieces, first slice 1.4 ms, worst slice 3.5 ms, peak 148 on screen.
Boss (slot 24 "Lift Bridge"): its stored solution (2 charges) did not reach a win inside the probe window (boss levels need more waves); the replay on the boss
level ran the same show (150 on screen, slice ≤ 2.2 ms). Same function as above, no boss-only path.
